# System Design

Use the Change Brief and repository evidence to define WHAT the system must do.

Include:
- scope/non-goals;
- actors and boundaries;
- responsibilities;
- contract/interface table;
- invariants;
- state/data/control flows;
- failure/recovery semantics;
- security/trust boundaries;
- reliability/idempotency/concurrency;
- observability;
- compatibility constraints;
- alternatives and rejected options;
- unknowns;
- requirement traceability.

Use Mermaid for diagrams where it improves verifiability.

Do not decide concrete files/classes/functions unless required to make a contract precise. Do not self-pass Gate A.
